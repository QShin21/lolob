RiftCast 0.3.0 前端呈现评审与修改建议
====================================

评审日期：2026-10-07。代码基线：`35455af`，`package.json` 版本 `0.3.0`。本文件为修改建议，业务代码保持原状。

0.3.0 已经具备完整的导播功能骨架，ARENA 的深色底、薄荷强调色和蓝红方身份也有一致性。下一阶段的前端工作应集中于操作区域重排、状态表达、字体与信息密度、表单编辑体验、观众端可读性。继续向长页面中追加面板，会增加临场查找和判断的负担。

本次重新构建了当前源码，并用独立演示数据运行本地服务。实际浏览了导播工作台、BP、实时数据、赛事与素材的四个分类、连接与输出、使用指南、赛后收尾、移动遥控，以及全部 11 种观众端场景。桌面检查使用 1366×768、1920×1080，移动页使用 390×844；节目画布截图为 1920×1080。制作面板的其他折叠内容、结果修订、席位和设备异常分支补充进行了源码检查。

截图和记录位于 `verification-output/frontend-review-0.3.0/`。本次没有启动真实 OBS，没有连接真实比赛、摄像头、麦克风或直播平台。离线演示环境没有装备、符文等完整静态缓存，截图中对应空位不能直接判定为生产环境的素材故障。浏览器包装截图中的深色空白也不代表真实游戏捕获画面。

待播隔离、同场景 TAKE、全局快捷键、危险动作按住执行、数据来源、人工 BP、音频控制、独立回放、结果修订和席位权限均已有实现。以下建议围绕这些能力的前端呈现展开。

实际观察到的几个问题，足以确定本轮修改的重点：

| 编号 | 观察条件与结果 | 对使用的影响 |
| --- | --- | --- |
| E01 | 1366×768、默认折叠状态，制作控制起点约 y=792；音频入口约 y=966，回放约 y=1126，选手画面约 y=1293 | 高频控制处于首屏以下，需要滚动查找 |
| E02 | 1920×1080 的连接与输出页约 6111 px 高；连接准备内容约 y=922，直播引擎标题约 y=1518 | 首屏优先展示了重复的制作控制，进入设置后不能直接开始连接准备 |
| E03 | BP 页的接管与规则标题约 y=1116，蓝红编辑槽位标题约 y=1592 | 大幅包装预览把实际 BP 操作推到了页面下部 |
| E04 | 实时数据页的十人数据表标题约 y=1344 | 大面积经济图占用首屏，选手信息需要滚动才能查看 |
| E05 | OBS 未连接，点击“回到比赛”，出现绿色背景、勾选图标和 `Not connected` 文案 | 失败消息具有成功提示的视觉特征，且错误未转为中文 |
| E06 | OBS 未连接，点击主工作台“切入节目”，提示“预监画面已切入节目”；来源摘要同时显示“已接收切入，正在应用来源” | 请求接收和画面完成的表达互相冲突 |
| E07 | ARENA 设置仍有“快捷开关即时同步到预监与节目”；底部配置仍有“已同步”“当前配置已应用” | 操作员难以区分已保存待播和已进入节目 |
| E08 | 1366×768 下，监视器标题约 9 px，场景名称 10 px，固定栏辅助文字 10 px，按钮文字 11 px | 多项关键文字需要集中注意力辨认，快速扫视较困难 |

这些坐标和尺寸来自当前演示状态的 DOM 测量，属于本次观察值。实际赛后状态、展开面板和系统缩放会改变页面高度。

建议以“导播正在播出时，关键操作在一个视口内可达”为主工作台的布局目标：

| 位置 | 建议内容 | 行为 |
| --- | --- | --- |
| 顶部固定状态栏 | 正在播出的战队与局号、当前场景、推流/录制、OBS/数据状态、控制席、待播修改数量 | 展示摘要；点击状态打开对应详情 |
| 左侧窄导航 | 工作台、BP、数据、赛事、设置、收尾 | 宽度稳定；紧凑模式可收为图标并保留名称提示 |
| 中部主要区域 | 大型 PGM 与中型 PVW | 保留目前三级画幅方向；保证比例和清晰的总线标签 |
| PVW 附近 | 待切场景、修改摘要、统一 TAKE、回到比赛、技术暂停 | 临场切换和应急按钮固定位置 |
| 右侧操作区 | 音频 / 回放 / 字幕 / 选手画面四个标签 | 每次展开一个任务面板；PGM 持续可见 |
| 底部 | 本阶段常用场景、播出顺序、精简健康信息 | 场景可固定和排序；其余通过“全部场景”打开 |
| 独立准备区域 | 比赛日七项检查、版本、设备拓扑、OCR 校准、资源下载、席位邀请 | 从当前任务入口进入，避免占用播出操作区 |

此布局为设计建议。最终宽高应在目标笔记本、外接显示器和 Windows 缩放环境中验证，避免通过持续缩小文字来容纳功能。

下面的通用修改适用于整个控制台。P0 表示影响播出判断或应急操作，P1 表示影响日常效率和可读性，P2 表示视觉完善或维护成本。

| 编号 / 优先级 | 当前依据 | 具体修改 | 验收方式 |
| --- | --- | --- | --- |
| F01 / P0 | `ProductionBar`、`ProductionDesk`、`StudioOutputDock` 分别展示部分播出状态；顶部还叠有面包屑、流程、比赛和阶段栏 | 合并重复的比赛信息。常驻显示 PGM 身份和输出摘要；PVW 身份与改动在预监旁展示。准备阶段显示完整流程，正式播出时收为当前阶段 | 任意页面均能直接读出“播什么、是否发送、是否录制、谁在控制”；1366×768 下关键操作无需滚动 |
| F02 / P0 | 只显示待播/已播版本号；旧文案与新隔离机制混用 | 统一五种状态：本地未保存、已保存到待播、切入处理中、引擎已应用、画面已人工核对。待播摘要显示“战队资料 2 项、字幕 1 项”等；版本号放详情 | 编辑并保存资料后明确提示待切入；OBS 未确认时不能显示播出完成；实时比赛采样不会被计入配置改动 |

| F06 / P1 | 多个 TAKE 入口名称不同；部分禁用按钮只依赖 title；危险按住按钮已有键盘支持但只有底色变化 | 所有 TAKE 入口共享动作组件、处理中状态和动态快捷键提示。禁用原因直接显示。按住动作加入进度条和执行对象名称，取消可见；保留现有输入框快捷键屏蔽 | 不同入口显示相同结果；配置快捷键后提示同步变化；按住未到时长不会执行，执行中反馈清楚 |

| F08 / P1 | 场景卡内部嵌套完整播出画布，辅助技术会读到大量选手/统计文字；已有部分焦点和 reduced-motion 样式 | 场景卡提供简洁可访问名称，缩略图内容标为装饰；补全标签页键盘操作、焦点可见、错误关联、提示播报。新的侧边编辑面板管理焦点和返回位置 | 键盘可完成准备、预监、切入、编辑和返回；读屏不会逐项朗读缩略图数据；减少动态效果偏好得到统一遵守 |

按钮高度建议以桌面 36–40 px、关键控制及移动触控 44 px 起步，这是本项目的交互目标。标准检查可参考 W3C 的[对比度要求](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)：普通文字至少 4.5:1，大号文字至少 3:1；[目标尺寸要求](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)规定了 24×24 CSS px 的最低目标及例外；[文字缩放要求](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)要求检查放大至 200% 时的内容和功能。当前页面尚未进行完整的无障碍合规审计。
