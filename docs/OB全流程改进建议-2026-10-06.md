# RiftCast OB 系统全流程改进建议

评估日期：2026-10-06。评估基线：RiftCast 0.2.0，当前本地提交 `604ba83`。

本建议按单台主观战电脑、一名导播兼顾镜头与播出的小型赛事组织；多人制作、独立回放机和备用观战机作为后续扩展。目标是让导播能持续看比赛、提前准备下一画面、及时处理故障，并保证选手身份、比分与数据正确。

本次依据当前源码、项目文档和独立内存复现进行评估。内存复现使用项目演示种子，没有连接真实游戏、操作 OBS、推流或写入赛事数据。以下验收数值均为建议目标，实际机器和平台需要演练确认。本文件是一份修改规格与现场流程建议。

## 一、当前基础与优先问题

当前已有单一 ARENA 包装、11 个场景、预监和节目、内置 OBS、BP 历史、OCR 经济、五组对位选手画面、自动归档、冻结赛后报告和下一局流程。这些功能可以继续使用。近期重点应放在播出隔离、比赛状态一致性、声音、回放和故障恢复。

优先级定义：P0 影响连续播出、身份或结果正确性；P1 影响操作效率、比赛叙事和观众理解；P2 适合完成基础演练后扩展。

## 二、赛前准备与开播

### R01 · 建立“比赛日配置”和一页开播检查（P0）

**现场情况：** 导播按时开播，OBS 显示已连接，但游戏捕获仍为空；换了声卡后解说无声；演示比赛、上一场标题或错误首发仍在节目中。

**具体修改：**

- 把赛事、系列赛、当前局、正式规则、蓝红方、首发、游戏账号、分路、照片和设备绑定放进同一个比赛配置。战队与选手具有稳定 ID；比赛中的游戏 ID 与播出名分别保存。
- 顶部“连接检查”拆成：比赛身份已核对、正确游戏来源已核对、数据样本匹配本局、音频已试听、录制路径与空间可用、节目内容已核对、平台已回看。OBS 连接只完成其中一项。
- 演示模式进入正式开播流程时给出明确状态；本场检查结果绑定配置版本，切换比赛、游戏来源或音频设备后只重置受影响项目。
- 对人工检查保留“谁在何时确认”；平台接收状态来自可用的实际反馈，无法自动确认时使用人工回看状态。

**验收：** 在断开游戏捕获、关闭麦克风、保留演示模式三种情况下，工作台分别指出准确的问题，导播能直接进入对应设置。完成一次 30 秒试录并检查回放声音、画面和同步。

### R02 · 提前准备离线素材与固定版本（P1）

**现场情况：** 场馆网络不稳定，BP 正在播出时英雄图片加载失败；比赛使用的补丁与静态装备价格、图标版本不同。

**具体修改：** 赛前一次性检查队标、首发照片、所有英雄图标、装备与技能图标、字体和赞助素材；补齐本地缓存并锁定本场静态资源版本。工作台并列显示比赛补丁、资源版本和 OCR 布局版本。联网更新安排在局间，由导播决定何时应用。

**验收：** 断开外网后走完待机、首发、BP、局内、赛后，各场景的核心素材可显示；版本不匹配有明确提示。Riot 说明 Data Dragon 可能晚于游戏补丁更新，地区客户端版本也可能与资源版本不同，因此应实际核对本场版本。[Riot Data Dragon 文档](https://developer.riotgames.com/docs/lol#data-dragon)

## 三、预监、节目与播出控制

### R03 · 隔离待播编辑，并完成一次整体切入（P0）

**现场情况：** 正在播比赛时，另一位工作人员准备下一场标题；导播调整选手画面时，希望先看裁切；字幕改到一半已经出现在节目中。

**具体修改：**

- 区分“工作区待播配置”和“已播配置”。标题、队名、比分纠正、字幕、包装开关、选手画面和静态布局先进入预监。
- 保持本局真实遥测继续更新，隔离人工配置；避免把比赛数据整体冻结而导致实时比分停止。
- 一次切入绑定场景、比赛内容、配置版本和相应来源；切入完成后显示“已应用版本”和来源状态。即使预监与节目场景名称相同，存在待播修改时也允许切入。
- 单独提供“立即播出字幕”“立即关闭图层”等明确操作，方便临场抢时；普通保存保持预监语义。
- 原生 HUD 处理与 OBS 摄像头更新具有异步结果，导播界面区分请求已接收、来源已应用、画面已确认；失败时保留可用画面并给出恢复入口。

**验收：** 节目保持局内时修改下一场标题、摄像头和字幕，实际录制中的相应内容保持原值；切入后一次完整生效。同场景更新与跨场景更新都可执行。

### R04 · 给动态预监提供可选实时模式（P1）

**现场情况：** 1 FPS 快照看起来正常，切入后才发现摄像头抖动、裁切错误、动画遮挡或转场黑帧。

**具体修改：** 保留当前 1 FPS 静态检查模式；桌面工作台增加可选的 30 FPS 原生预监或经过性能验证的视频预监。开始时仅为需要动态核对的主预监启用，其余缩略图继续低频。注明当前预监显示方式、帧龄和是否拥有独立视频来源。动态预监使用原生投影时同时提高预监浏览器来源帧率。

**验收：** 游戏、摄像头、HUD、OCR、录制和推流共同运行时比较开关预监的性能；确认预监与节目能分别显示不同待播配置，运动连续且没有新增明显渲染或编码丢帧。不要把截图轮询直接提至 60 FPS。

### R05 · 固定常用控制与独立应急操作（P0）

**现场情况：** 导播在改数据页面时突然发生团战；客户端闪退；一条错误字幕需要立刻撤下。

**具体修改：** 固定显示节目、下一待播画面、切入、回到比赛、关闭分析图层、关闭选手画面、技术暂停六类控制。增加可配置的明确组合键和控制面板映射，保留输入框的正常打字行为。记录前一个可用节目，用于撤回最近一次人工切换；撤回范围限定在人工播出操作。

技术暂停画面在 OBS 内另建本地静态来源，不依赖 RiftCast 网页服务；提供 OBS 原生备用热键或硬件按钮。服务断开时已播画面尽量延续，工作人员仍能用引擎自身控制切到备用画面。停止推流、载入其他比赛、新系列赛等操作采用明确按钮区隔和按住执行，普通切镜保持迅速。

**验收：** 在编辑页面、程序前台与游戏前台分别演练应急操作；主动关闭界面服务后，OBS 备用控制仍能切出技术暂停画面。按键冲突和误触通过录制回看确认。

## 四、BP、阵容与加载阶段

### R06 · 分开 BP 顺序与最终选手归属（P0）

**现场情况：** 蓝方第一选抢射手，第三选拿摇摆英雄，最后十秒交换英雄；观众看到的姓名和位置提前绑定，解说被错误提示误导。

**具体修改：** BP 进行时按 B1 / R1 等动作顺序显示英雄，分开预选、已锁定和最终归属。最终阵容使用“选手 ID—英雄—确认分路”映射，锁定和交换完成后进入首发对位。未确认分路不按数组顺序自动贴上单、打野等标签。手工拖动换位后能选择锁定，工作台同时保留客户端新样本供核对。

**验收：** 先选下路英雄、摇摆英雄、双方交换、名单乱序、API 无分路五种情况中，预选不会提前归档，最终英雄、选手名、照片和分路一一对应。

### R07 · 增加赛事规则与人工接管（P1）

**现场情况：** 普通 BP 被全局禁选拦住；重开 BP 产生无效历史；LCU 断开后导播手工补齐，却被下一次同步覆盖。

**具体修改：**

- 每个系列赛明确设置普通 BP、全局禁选或赛事自定义规则；禁用范围、重赛历史处理和例外局条件按实际规程配置。
- BP 模式分为自动同步、人工接管、差异核对。人工接管期间后台继续读取客户端，待播内容保持人工值，恢复自动前显示差异。
- 增加回退一步、清空本次无效 BP、继续上次 BP、裁判确认例外等操作，保留理由与操作历史。
- 全局已用英雄按稳定战队和局身份保存，换边后跟随战队；重赛与正常下一局使用不同动作。

**验收：** 普通 BO3 可以重复选英雄；全局规则按照已配置范围限制；取消或重开 BP 不污染历史；手动值能够稳定保留，恢复自动时能明确处理冲突。LCU 的兼容变化缺少保证，人工接管需要作为常规备用路径。[Riot League Client API 文档](https://developer.riotgames.com/docs/lol#league-client-api)

### R08 · 处理加载、掉线与首次进局（P1）

**现场情况：** BP 结束后迟迟未进入比赛；一名选手重连；观战电脑重新打开客户端；游戏首帧、名单和时钟先后就绪。

**具体修改：** 增加“BP 已完成 / 加载中 / 等待游戏信号 / 进局核对 / 已播局内”的操作状态，可复用 ARENA 待机版式。进局核对正确游戏窗口、十人身份、蓝红方、时钟、装备和采集区；数据不足时保持已有 BP 或等待画面。LCU 大厅等待、未启用 Replay API 和局内信号中断分别提示。

**验收：** 游戏晚于 BP 30 秒进入、客户端重启、十人名单先到但画面未到时，系统不会自动切出空的局内节目，也不会把等待状态表示成错误结算。

## 五、比赛中镜头、信息与选手画面

### R09 · 把镜头操作放到导播主流程（P1）

**现场情况：** 导播忙于切经济图，漏掉打野绕后；边路单杀与大龙同时发生；镜头在团战中反复跳人，观众失去空间关系。

**具体修改：** 工作台增加十名选手跟随、取消跟随、手动镜头、双方战争迷雾、观战常用视图的操作提示或可验证控制。先实现当前客户端能够稳定执行的能力，其余保留清楚的游戏快捷键提示。支持配置单屏主控、双屏观战布局，展示实际键盘控制对象，避免误按在浏览器上。

把经济领先、近期击杀、已发生的资源事件和人工提示汇成“建议关注”条，只向导播提示。团战过程中保持稳定全景，跟随关键动作时避免频繁改变主体；清理战斗后再展示装备或经济。击杀事件通常只能提示已发生的结果，提前关注仍依赖导演对小地图、兵线、打野路线和站位的观察。自动导播在有充足实机样本后作为 P2 独立试验。

| 实际比赛情境 | 导播镜头与操作 | 系统应提供的帮助 |
| --- | --- | --- |
| 对线平静，打野准备越塔或进入河道 | 提前交代兵线、人数与绕后入口，镜头保留受威胁的一侧和支援方向 | 快速跟随目标选手、显眼的小地图、人工危险标记 |
| 单杀已经发生 | 先拍到交战结果与后续推进；有安全空档再用短回放补开战过程 | 击杀时间标记、保存此前缓冲、待播队列 |
| 大资源争夺，侧面有人绕后 | 使用足够宽的视角交代正面与侧翼，临近开团时撤下分析 | 资源提示、一键撤回图层、保持选手画面 |
| 资源区团战与边路推高地同时发生 | 根据即时胜负影响选择主镜头，在有条件时用第二路画中画；只有单路时先保住关键事件，随后补另一处回放 | 清楚标注视频来源能力、多事件提示和片段标记 |
| 团战结束，残血选手被追击 | 连续跟随追击与存活结果，结束后交代队伍获得的资源 | 快速选人跟随、返回全景、人工结束关注 |
| 基地推进与可能一波结束 | 保持基地及可防守英雄在画面中，胜负画面结束后再进入结果包装 | 暂缓分析与轮播、终局候选状态、导演选择赛后播出时机 |

当前只有一份游戏捕获时，调整观战镜头会同时影响节目和预监。真正独立准备另一处游戏视角需要第二观战来源；第一阶段应把下一镜头意图和关键控制做清楚。

**验收：** 从选手跟随转手动镜头、从设置页返回游戏操作都能快速完成；事件提示不会自动抢镜。录像中能连续看清开团位置、关键动作和战斗结果。

### R10 · 给分析画面定义播出时机（P1）

**现场情况：** 十人经济排行盖住龙区开团；大装备差解释尚未讲完，已经爆发下一次战斗。

**具体修改：** 经济曲线、排行和详细装备图层具有人工可设置的播出时长和一键撤回。导播可在安全空档预监、切入，遇到战斗立即回到比赛。分析窗口优先使用小范围、短时展示；选手数据表的展开与关闭不要求进入深层页面。事件时间线、待播提示、输出健康状态放在主工作台可见位置。

**建议时机：** 对线安全空档介绍对位；回城或大资源争夺结束后展示关键装备；团战发生后先呈现结果，再安排短回放；即将逼近关键目标时保持场内视野。

**验收：** 分析图层从播出到撤回只需要一个操作。导播能在分析播放时持续看到未被图层覆盖的比赛监视器。

### R11 · 保持局内画面清楚，并按接收端验收（P1）

**现场情况：** 桌面大屏看得清，手机直播间里的选手 ID、KDA 和装备变得难读；底部过多实时状态显示未知，观众无法快速比较。

**具体修改：** 保留已确认的中央不透明计分板、原生英雄区域和小地图，以及当前原生团战视图。提高最核心的队名、局号、比赛时间、KDA 和补刀辨识度；详细装备与扩展状态按需要调用。仅在有有效来源时显示血量、资源、经验、大招等动态状态，避免未知值占用过多阅读空间。

使用实际 OBS 合成并经过平台压缩的画面核对字号、颜色、裁切和遮挡。长中文 ID、双位击杀、长装备名、队标比例异常均纳入素材验收。

**验收：** 在 1920×1080 本地录制和手机接收画面中核对同一场团战，保留英雄属性、目标区域和小地图；低码率下核心比分仍可辨识。

### R12 · 显示可用数据，并核对对位与时间（P0）

**现场情况：** 游戏计分板切到装备页，累计经济停止采样；左右两名选手金币样本相隔较久；API 无分路却按返回顺序排列；数据缺失时资源数显示 0。

**具体修改：**

- 主工作台显示团队经济、个人经济和 KDA/CS 的完整度与样本年龄；保留已有失效规则，缺失与真实零值分别处理。
- 建立稳定的选手账号与分路映射；API 暂缺分路时使用本局已确认映射，未确认时停用“对位领先”结论。
- 对位经济差只比较同局、同一时间段且都有效的累计经济样本；统一有效 API 与 OCR 样本规则。当前 `bottomGoldDifference` 只接受 OCR，未来拿到可信 API 累计经济时也要显示一致结果。
- 保留 OCR 原文、画面精度与原始游戏时间。团队 HUD 只显示到 0.1k 时，经济差显示相同精度或明确估计，避免制造个位数精度。
- 分别记录采集时间、画面对应游戏时间与播出时间；回放、暂停、跳转、跨局时清理或隔离样本。
- 数据中断、图像采集失败、名单冲突、全部金币过期具有不同恢复入口；播出端简洁显示未知或必要提示，诊断详情放在工作台。

**验收：** 遮挡采集区、切金币/装备页、交换分路、恢复 API、跳转回放后逐项对照原始游戏帧。错误身份与过期样本不生成领先值，恢复时不串局。

### R13 · 建立资源争夺提示（P1）

**现场情况：** 导播只看到击杀提示，未提前关注双方绕后和资源区站位；补丁改变资源种类或刷新规则，旧倒计时继续显示。

**具体修改：** 根据本场版本资料、可靠事件和确认的游戏时间，显示可验证的资源生成、击杀、争夺和增益剩余时间；无法确认的计时保留未知。资源规则放在版本配置中。大龙、小龙及本版本存在的其他关键目标具有人工标记入口；低置信信息仅提示导播核对。

**验收：** 更新版本配置后目标类型与规则正确；游戏暂停时倒计时按可靠游戏时钟停止；跳转、缺失事件或无法确认增益时停止显示推算值。对每个资源提示都能找到来源或人工确认记录。

### R14 · 选手画面采用“准备、切入、保持”（P1）

**现场情况：** 五秒轮播在关键反应镜头上切走；USB 摄像头断开，节目出现黑框；第二局换边，队名与摄像头错配。

**具体修改：** 保留五组对位，绑定到战队与选手。导演可预监下一组、切入后固定，或在安全阶段恢复轮播；团战、回放、技术暂停期间提供明确的保持策略。摄像头断开时撤下该窗口或使用对应照片，工作台显示实际应用失败与重试状态。换边一次完成摄像头、照片与名牌重新映射。

**验收：** 手动保持不会被轮播计时打断；拔掉摄像头后核心比赛区域继续正常播出；下一局换边时十名选手设备映射与姓名一致。

## 六、声音、回放、推流与事故处理

### R15 · 增加直播中可用的音频台（P0）

**现场情况：** 解说说话时游戏声音过大；麦克风突然失效；直播监听被系统音频再次采集形成回声；采访开始后选手话筒未进入节目。

**具体修改：** 在工作台固定显示游戏、解说、采访、音乐、回放的电平与静音状态。先完成游戏和解说的实时音量、静音、试听，后续扩展其他总线。设备重连状态、削波提示和持续无输入提示面向操作员；提醒条件结合应当有声音的操作状态，避免把安静片段判断为故障。

把不改变设备拓扑的音量、静音、预先建好的增益/限幅控制允许在输出期间操作；重新配置编码和采集设备仍放在明确维护流程。区分监听和节目发送，单独设置回放声音、背景音乐与现场解说的组合；原声、解说和成品分轨保存。

**验收：** 用游戏音效、真实讲话、采访输入和播放回看测试混音；回声、爆音、无声能够被发现并当场调整。多轨录制重开后可分别播放。OBS WebSocket 已提供电平事件、音量、静音和音频同步控制，可按捆绑运行时的实际可用请求逐项接入。[OBS WebSocket 官方协议](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)

### R16 · 回放使用独立视频片段与待播队列（P0 保护，P1 制作）

**现场情况：** 直播中在同一个观战客户端按暂停或跳转，当前节目也跟着倒退；团战回放尚未结束，现场又出现击杀；回放镜头叠上了当前局内时钟。

**具体修改：**

- 当前比赛来源正在播出时，在服务端保护该来源的暂停、跳转和倍速操作；离线录像制作明确标注当前受控客户端。
- 接入内置 OBS 的回放缓冲与保存片段。先采用已录节目片段，保留片段中原有比分，回放期间关闭当前实时 HUD；需要干净画面时再增加独立游戏画面录制来源。
- 增加“标记精彩、保存片段、入点/出点、预监、切入、立即回到比赛”链路。建议从事件前约 8–12 秒到事件后约 5–8 秒开始，允许导演调整；缓冲时长按机器资源试验，初始可设 60–90 秒。
- 回放播放期间持续显示独立的当前比赛监视器；带明显回放标识，声音策略由导演提前选择。新战斗发生时一键中止片段并回到比赛。
- 慢速、多角度和独立回放机作为后续能力，匹配本场 game ID、片段时间与播出素材。

**验收：** 回放节目切入时原游戏客户端和直播数据继续向前；片段不会显示当前时间或错误实时金币；中途发生战斗能即时回到比赛。Riot 的 Replay API 会直接修改本机回放播放状态；OBS 提供独立的缓冲启停与片段保存请求，两条链路需要明确处理。[Riot Replay API](https://developer.riotgames.com/docs/lol#replay-api)、[OBS WebSocket 回放缓冲协议](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md#startreplaybuffer)

### R17 · 在主工作台显示完整输出健康（P0）

**现场情况：** 节目监视器流畅，但平台卡顿；OBS 仍在重连；录制磁盘快满；节目来源丢失而 OBS 合成 FPS 保持正常。

**具体修改：** 把已有渲染、编码、网络丢帧和码率从设置页摘要到主工作台，新增统计窗口、重连持续时间、视频来源状态、录制时长和剩余空间。分开显示 OBS 引擎连接、游戏源就绪、推流发送、平台接收与录制写入状态；任何无法确认的环节保留待确认。

告警带具体动作：渲染负荷高先减少非必要预监与图层；编码负荷高使用已演练的输出配置；网络丢帧检查上行与服务器；摄像头失效撤下对应窗口；磁盘不足关闭非必要文件输出并转到预先准备的路径。输出期间不能热改的参数注明维护窗口。重复告警合并并可确认，恢复要重新稳定观察。

建议以滚动 5–10 秒窗口做提醒，并在现场设定阈值，例如某类丢帧持续超过 1% 时提示；该数值仅用于演练起点。来源卡死判断结合采集健康、游戏时钟和实际变化，避免仅凭像素相同把暂停或静态画面判成故障。

**验收：** 人为限制上传带宽、拔摄像头、停止游戏来源和降低可用磁盘空间分别得到不同提示；验证应在安全测试环境进行。本地录制与接收端同时回看，区分渲染/编码问题与网络丢帧。[OBS 性能排查](https://obsproject.com/kb/encoding-performance-troubleshooting)、[OBS 网络丢帧排查](https://obsproject.com/kb/stream-connection-troubleshooting/)

### R18 · 为技术暂停、恢复和重赛建立不同流程（P0）

**现场情况：** 选手掉线，裁判宣布暂停；观战电脑断开但比赛还在进行；开局重赛需要复用阵容或重做 BP。

**具体修改：** 操作员区分比赛正式暂停、播出信号故障与录像暂停。正式暂停显示经确认的原因、现实经过时间与恢复提示，游戏时间按实际来源处理；信号故障保留节目连续性并切出本地备用画面；重赛另建尝试编号，保留被作废记录，比分与全局历史按赛事规则处理。

恢复前核对游戏身份、十人映射、时间与声音，重新取得有效样本。信号恢复只提示就绪，由导播选择播出时机；自动重新绑定到同名窗口时也须核对客户端身份。

**验收：** 正式暂停、观战电脑掉线、客户端重开、前两分钟重赛四种场景走完整流程。局号和 BO 比分保持正确，未知统计不沿用到新尝试。

## 七、局间、结果纠正与赛后

### R19 · 统一下一局，并把 BO 比分绑定战队（P0）

**现场情况：** BP 页提前点下一局；双方换边后比分归属反转；下一局准备覆盖仍在播的上一局内容。

**具体修改：**

- 所有下一局入口使用同一服务端动作与校验；普通资料编辑不能间接绕过局间状态机。
- 系列赛比分按战队 ID 保存，本局蓝红方是映射。一次换边同时重映射比分、历史、选手名牌、照片、摄像头和数据匹配。
- 将“准备下一局”与“播出下一局”分开。准备阶段新建当前工作区，节目绑定上一局内容或已切出的局间报告；本局内容变更在切入时生效。
- 扩展冻结上下文到仍可播出的上一局画面，避免仅保护赛后和排名场景。

**验收：** A 战队领先 1:0，换到红方后仍显示 A 1:0；BP 页与结算页在胜方未确认时表现一致；节目保持上一局 `live`、`postgame` 或采访时准备下一局，画面身份和时间都稳定。

### R20 · 支持结果纠正和终局完整度（P0）

**现场情况：** 人工误选胜方；裁判改判；客户端结束阶段先到，但最后一帧 KDA 尚未取得；观战画面有延迟，后台结果先于画面到达。

**具体修改：** 在已有终局补样与冻结报告基础上增加“纠正本局结果”，展示影响的比分、赛程、归档和系列赛是否结束；保存旧结果、理由和新版本，再按有效结果重新计算 BO 比分。结果缺少、样本待到达或裁判待确认分别显示。

结算资格与播出时机分别判断。后台可以先保存候选结束信号，确保归档游戏身份匹配；节目继续按观战画面的时间与导播选择播出，避免提前更新胜负和透露结局。重复结束事件不得重复计分。

**验收：** 改判后当前显示、赛程、历史、导出一致；重复 GameEnd 不加分；有延迟的观战画面仍在团战时不提前出现胜方。终局样本不足的报告保留缺失状态，不把最后观察值标成完整终局统计。

### R21 · 形成“本局结束—局间—下一局”的短流程（P1）

**现场情况：** 推平后导播来回切管理和设置页面；错误地结束整场推流；系列赛最后一局与普通局间处理相同。

**具体修改：** 结算栏提供胜方核对、赛后数据、精彩片段、采访、下一局准备和系列赛结束分支。局间可持续推流与录制，节目按赛后报告、解说/待机、下一局 BP 顺序推进；只有整场结束进入输出收尾。倒计时由实际准备情况控制，工作人员可调整并留下原因。

**验收：** 完整走完 BO3，无需中断推流；上一局报告与视频仍能访问。最后一局结束后给出收尾入口，并核对片尾、停止输出和保存。

### R22 · 把数据归档与视频文件关联（P1）

**现场情况：** 已保存比赛统计，却找不到对应录制；同一天多个 BO3 文件混在一起；界面显示已保存，磁盘写入实际失败。

**具体修改：** 按赛事、日期、系列赛、局号和尝试编号建立文件索引。每局记录视频路径、录制起止、游戏时间与视频时间的映射、精彩标记、数据来源与最终版本。保留当前 MKV 录制和原子状态文件保存；加强写入失败反馈与耐久保存确认，只有确认磁盘写入后显示已保存。

停止录制后检查文件存在、大小和可播放性；导出赛事包可包含资料、终局 JSON/CSV、片段索引和文件清单，敏感输出凭据继续留在本机受控配置。保留当前记录数量限制时，超过限制应有可见的归档策略。

**验收：** 连续两场系列赛归档后，每局都能打开对应文件；模拟写入失败时明确提示保存未完成；结束进程再启动，已确认保存的结果、改判和视频索引完整。

## 八、多人协作与长期使用

### R23 · 设置操作席位、版本冲突与制作提示（多人使用时 P0）

**现场情况：** 手机遥控与主机同时改预监；数据席保存旧名单覆盖新名单；解说不知道导播准备播出什么。

**具体修改：** 角色分为只读、资料、字幕、回放、主导播；切入节目和局号推进由当前控制席执行。服务端记录控制权、操作人、请求 ID、预期配置版本；过期编辑先展示冲突，重复请求不重复执行。控制权有明确接管流程。

建立可人工编排的待播顺序，显示下一画面、预计时长、准备状态与“预备/已播”确认。制作提示仅在操作员界面显示；带平台延迟的解说返送与当前观战画面返送分别命名，选择对应时钟。

**验收：** 手机和主机并发操作时只有授权控制席切入；旧表单不能覆盖新版本；解说能清楚看到导播已准备的回放或分析，并按正确返送讲解。

### R24 · 在场次之间完成维护与兼容核对（P1）

**现场情况：** 游戏更新后 HUD 比例改变、OCR 区域失效；现场才首次下载运行时；帮助页关于摄像头和收尾的说明与当前功能不同。

**具体修改：** 比赛日前完成运行时准备、资源缓存、客户端字段探测和 OCR 布局校准；记录当前代码、OBS、游戏、资源与识别配置版本。维护更新放在停播窗口，提供上一套经过演练的配置恢复方式。逐页核对帮助、README、功能表、按钮名称和实际状态；统一 1 FPS 预监、内置摄像头和“局间持续播出”的说明。

**验收：** 同一版本有明确的字段与布局验证记录；首次离线启动无需临场下载；导播按帮助页能完成当前流程。自动摄影、胜率模型和独立多路回放在基础流程完成后独立验收。

以上是功能依赖顺序，工期需要完成设计和目标机器演练后估算。多人同时控制节目时，R23 的基本角色与控制权保护应提前至第一批；完整的制作提示与多机扩展仍可后置。基础阶段只维护一套 ARENA 包装；复杂动画与新模型放在实际播出问题处理之后。

## 十、交付验收应是一场完整转播

建议先进行一场完整 BO3 排练，并同时保存节目录像、原始观战参考帧、状态日志和平台接收回看。每个开发批次仍需运行与变更相符的服务、类型与构建检查；代码检查和现场验收分别记录。

| 场景 | 必须观察的结果 |
| --- | --- |
| 赛前断网、资源缺失、错误设备 | 开播检查指出具体问题，已缓存素材可用，试录声音可核对 |
| BP 先抢下路英雄、交换英雄、人工接管、普通/全局规则 | 选取顺序与归属准确，人工值稳定，历史符合本场规则 |
| 节目中编辑字幕、队名、下一场资料 | 编辑先进入待播，确认切入后完整应用 |
| 主工作台、编辑页和游戏前台发生团战 | 快捷操作对象明确，快速关闭分析并保持比赛视野 |
| 金币列隐藏、采集区遮挡、角色缺失、恢复采样 | 缺失与真实零值分开，未知对位不显示领先，恢复不串局 |
| 直播回放、同时出现第二次战斗 | 主比赛持续向前，片段身份/时间正确，可即时返回 |
| 麦克风失效、监听回声、摄像头拔插 | 声音和选手窗口可单独处理，核心节目继续播出 |
| 限制上传、OBS 重连、网页服务中断 | 告警分类准确，录制状态独立，OBS 本地备用场景可用 |
| 改判、重复结束事件、终局样本晚到 | 比分只计一次，纠正结果一致，未完成统计保持待确认 |
| 换边、旧样本滞后、节目保持上一局再准备下一局 | 比分/照片/摄像头随战队，节目身份稳定，新旧局隔离 |
| 重赛与正常下一局 | 尝试编号、BP 历史、BO 比分按规则处理 |
| 保存失败、磁盘不足、结束后重启 | 失败可见，已确认数据完整，视频与比赛一一对应 |
| 手机与主机并发编辑 | 控制权与配置版本校验生效，节目不会被抢切 |

性能验收至少包含游戏、全套实际 HUD、当前所需摄像头、OCR、录制和推流共同运行的连续 30 分钟；核对实际显示、渲染、编码、网络和接收端播放，同时覆盖暂停恢复与回放切入。先以无非预期黑帧、无错人错比分、无未标注的失效统计、音画同步在人工回看中可接受为通过条件，再根据设备设定量化目标。
